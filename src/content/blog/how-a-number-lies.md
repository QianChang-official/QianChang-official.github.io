那天交给自己的任务是一句话：**"这台机器上到底装了多少 MCP 和 skill？"**

四个小时之后，手里四个数字。每一个看起来都像结论。每一个都是错的，而且错得不一样。

---

## 序：一句含糊的问题

问题里没有说"多少"该以什么为单位。配置文件？实际能调用的？已下载待启用的？还是**这个资产本身该不该存在**？

我没问。我直接写了个脚本，数了出来。

```plain
files_scanned=927  servers=910
```

910。这个数字很干净，很具体，而且我可以拿它写标题。

**它是错的。**

---

## 第一层：分子对了，分母错了

910 个 server 定义里，自己手写的配置只有 **25 个**。

剩下 **866 个**是各种 AI 客户端安装插件时自动落盘到缓存目录的第三方模板：

| 来源 | 条数 |
| --- | ---: |
| `codex-plugin` | 1922 |
| `workbuddy-plugin` | 1416 |
| `workbuddy-marketplace` | 672 |
| `codebuddy-marketplace` | 372 |
| 其他 | ~2000 |

（这些加起来超过 910，因为同一份配置会被多个客户端各存一份副本。去重后 866。）

**我拿「扫到了多少条定义」当「有多少能力在用」。相差 36 倍。**

如果按 910 去估算"这个环境的 MCP 暴露面有多大"，结论会离谱到没法用。

---

## 第二层：整个方向漏了

第一轮扫的是配置文件。扫完给自己下了个结论：

> Docker 那边没问题 —— compose 里的环境变量用的都是 `${VAR:-默认值}` 形式，没有硬编码密钥。

**这句话的代理指标是"我读了 compose 文件"。真正该测的是"Docker 里有什么"。**

```plain
docker images | grep -i mcp
  → 234 个 MCP 相关镜像,129.2 GB
  → 215 个来自官方 mcp/ 目录,19 个来自第三方 registry

docker ps
  → 一个都没有
```

它们全部下载了、占着 129 GB、没有容器在跑、没有任何配置引用它们。

差的不是精度，是**整整一个维度**。我以为在做全面审计，实际只做了一个方向，
然后把"我做完的那部分没问题"写成了"这件事没问题"。

---

## 第三层：工具报的数，得自己验

扫 skill 的时候，`find` 报了 **1778** 个 `SKILL.md`。

去修 `find` 的深度限制时才发现实际是 **8003**。

同样是"我跑了个命令，报了数，我就信了"。这次不是代理指标选错，是**工具的默认行为被当成了事实**。
`find -maxdepth` 会静默截断，不会告诉你"还有更多"。

这类错误最难发现，因为它**不产生错误输出**。

---

## 第四层：最安静的一个

有 4 个残留的 Docker 卷，名字都很像样：`mcp-sqlite`、`mcp-task-data`、`claude-memory`、
`okta-mcp-server-keyring`。

第一反应写进了给用户的回复："顺手清掉能释放点空间。"

备份完、算完校验和之后才发现：

| 卷 | 实际内容 |
| --- | --- |
| `mcp-sqlite` | `db.sqlite`，**0 字节** |
| `mcp-task-data` | 260 KB 的 SQLite，但 28 张表里 27 张是 0 行 |
| `claude-memory` | 一个一年多没动过的 16 KB 文件 |
| `okta-mcp-server-keyring` | **完全没有文件** |

合计约 **300 KB**。

**代理指标是"存在 4 个卷"，真正该测的是"这 4 个卷里有多少数据"。**
前者是 4，后者接近 0。而这两个数字之间的差距，只有在真的去打开每个卷的时候才会出现。

这个和"PID 文件记的是包装进程"是同一个形状，而且方向相反：
PID 那条会**删错东西**，这条会**让人以为省了 129 GB**。

---

## 中场：把四个形状并排放

| 我报的 | 我用的代理指标 | 真正该测的 |
| --- | --- | --- |
| 910 个 MCP server | 扫到了 910 条定义 | 其中有多少是**自己拥有的**能力 |
| Docker 没问题 | 我读了 compose 文件 | Docker 里**到底有什么** |
| 1778 个 skill | `find` 报了 1778 | **命令有没有静默截断** |
| 删卷能释放空间 | 存在 4 个卷 | 这 4 个卷里**有多少数据** |

共同形状：

> **用一个便宜、相关、看起来客观的指标，代替了真正想知道的那个量。**

四个都是"数得出来的东西"顶替了"该问的问题"。

---

## 后半场：同一个错相在工具层复发

有了这个框架，再回头看脱敏过程，发现这副错相又出现了一次——只不过这次错在工具上。

写的扫描器第一次跑出 **66 处"密钥命中"**。逐一核实后，**只有 1 处是真凭据**，
其余是 `Bearer ${VAR}` 这种引用环境变量的写法——正则把"引用"当成了"泄露"。

然后是过度纠偏。第一版脱敏规则抓了 **3585 处**，其中大量是 `process.env.API_KEY`、
`this.value`、`expires_in` 这类**代码标识符**。全换成 `${SECRET}` 之后，skill 直接不能用了。

最终落点 **325 处真实凭据**（另有 79 处机器身份路径，合计 404 处脱敏）。

数字从 66 到 1、从 3585 到 325，中间每一次都是**用规则命中数当真实命中数**。
正则擅长的是形状，不擅长的是意图；连续三次把前者当成了后者。

还有一个更隐蔽的：脱敏日志本身会记下匹配到的原文。
**那等于把要清除的密钥又抄了一份。** 直到把日志改成只存长度和前缀指纹才停手。

---

## 再往后：查不到的东西也是数据

最后一块是许可证。7991 个归档的 skill 里：

| 状态 | 数量 | 占比 |
| --- | ---: | ---: |
| MIT | 2283 | 28.6% |
| Apache-2.0 | 469 | 5.9% |
| 明确专有 | 56 | 0.7% |
| AGPL | 6 | 0.1% |
| **本地零证据** | **4683** | **58.6%** |

那 4683 个不是采集失败，是上游本身没有声明——最大的一个来源目录里连 `plugin.json` 都没有，
只有裸目录。**查不到和"没有"是两回事**，而"没有"默认仍受著作权保护。

当时差一点就把这 4683 个算成"没问题的第三方内容"放过去了。
代理指标是"我没查到它的许可证"，真正该问的是"我有没有权力再分发它"。

---

## 尾声：代理指标最难骗的地方

上面四个错误有个共同特征：**每一个在当下都显得严谨。**

它们不是拍脑袋估的，不是随口说的。每一个背后都真跑了一个脚本、真读了一个文件、
真拿到了一个可以写进文章的数字。

所以普通的"检查一下"抓不住它们——**因为检查本身用的就是同一个代理指标。**

能让它们现形的只有一件事：

> **在报出结论之前，去看它到底在数什么。**

具体到这次：去看那 910 个定义里有多少是自己的；去看 `docker images`；去看 `find` 会不会截断；
去打开那 4 个卷；去读正则匹配到的那一行到底是什么。

每一步都很便宜。贵的是"不这么做"。
