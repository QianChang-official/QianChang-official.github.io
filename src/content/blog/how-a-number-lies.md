给自己的机器做了一次 MCP / skills 资产盘点，想搞清楚一个问题：**这机器上到底有多少能力在用？**

四个小时之后我手里有四个数字。每一个看起来都像结论。

其中一个还被我当成"发现了一个真实泄露"发了出去。它不是。

这篇记录那几个数字是怎么错的，以及我为其中一个错误付了什么代价。

---

## 先说我不做什么

这次盘点有几件事是**一开始就决定不做**的，先划出来：

- **不公开那 4683 个查不到协议的 skill。** 无声明不等于可自由使用，默认仍受著作权保护；
- **不把"我没查到它的许可证"记成"它没有许可证"**——这两件事的差别就是能不能再分发；
- **不用任何占位符去糊弄空值。** 查不到就写"未声明"，不写"MIT"也不留空。

这三条划下来，后面能公开的就只有 3308 个。它们里面的绝大部分同样是厂商内容，
但至少每一条的授权状态是可查的。

## 起点：一句含糊的问题

问题里没说"多少"该以什么为单位。配置文件？实际能调用的？已下载待启用的？还是**这个资产本身该不该存在**？

我没问，直接写了脚本数。

```text
files_scanned=927  servers=910
```

910。这个数字很干净，很具体，我可以拿它写标题。

**它是错的。**

---

## 第一个数字：分子对了，分母错了

910 个 server 定义里，自己手写的配置只有 **25 个**。

剩下 **866 个**是各种 AI 客户端安装插件时自动落盘到缓存目录的第三方模板：

| 归属 | 数量 |
| --- | ---: |
| `workbuddy-plugin` | 276 |
| `workbuddy-connector` | 260 |
| `workbuddy-marketplace` | 243 |
| `codex-plugin` | 44 |
| `workbuddy-ai-plugin` | 22 |
| 其他 | 21 |

**WorkBuddy 三个市场合计占 90%。**

25 + 866 = 891，和 910 差 19 条——那 19 条来自无法归入任何一类的路径
（散落在聊天客户端缓存、下载目录里的零散配置）。**不补这个差，就又要用一个
"凑得上的数"代替真实的数。**

**我拿「扫到了多少条定义」当「有多少能力在用」，相差 36 倍。**

如果按 910 估算"这个环境的 MCP 暴露面有多大"，结论会离谱到没法用——而 910 本身看不出任何问题。

> **补记（发布后被人核对才发现）**：这篇文章的第一版里，上面那张表我填的是
> `codex-plugin 1922 / workbuddy-plugin 1416 / workbuddy-marketplace 672 / codebuddy-marketplace 372`。
> 这四个数是 **skill** 的来源分布，不是 MCP 的——我从另一个清单里直接抄了过来。
>
> 方向恰好相反：那张表暗示 MCP 生态以 Codex 插件为主，真实主力是 WorkBuddy 的三个市场。
>
> 而且我在表下面加了一句"同一份配置有多个客户端副本，去重后 866"，这句话也是错的——
> 那份 CSV 的 866 行**已经是去重后**的（`server` + `config_path` 的唯一组合数正好是 866），
> 不存在需要再去重的副本。
>
> 这张表是用来论证「分子对了分母错了」的。**而它本身就是分子分母搞错了。**

## 第二个数字：整个方向漏了

第一轮只扫配置文件。扫完给自己下了个结论：

> Docker 那边没问题——compose 里的环境变量用的都是 `${VAR:-默认值}` 形式，没有硬编码密钥。

**这句话的代理指标是"我读了 compose 文件"，真正该测的是"Docker 里到底有什么"。**

```text
docker images --format '{{.Repository}}' | grep -c mcp
  → 234 个 MCP 相关镜像

docker images --format '{{.Repository}}\t{{.Size}}' | grep -i mcp \
  | awk -F'\t' '{s+=$2} END {print s}'
  → 129.2 GB

docker ps -a --format '{{.Image}}' | grep -ci mcp
  → 0
```

215 个来自官方 `mcp/` 目录，19 个来自第三方 registry，占着 129.2 GB，
**没有容器在跑，没有任何配置引用它们。**

差的不是精度，是**整整一个维度**。我以为在做全面审计，实际只做了一个方向，
然后把"我做完的那部分没问题"写成了"这件事没问题"。

## 第三个数字：工具报的数，得自己验

扫 skill 时 `find` 报了 **1778** 个 `SKILL.md`。

去修 `find -maxdepth` 的限制时才发现实际是 **8003**。

```text
find ~ -maxdepth 7 -iname SKILL.md      →  1778
find ~           -iname SKILL.md        →  8003
```

同样是"我跑了个命令，报了数，我就信了"。这次不是代理指标选错，
是**工具的默认行为被当成了事实**——`-maxdepth` 静默截断，不会告诉你"还有更多"。

这类错误最难发现，因为它**不产生错误输出**。命令返回 0，结果是一个列表，看起来完全正常。

> 写完初稿之后有人来复核，当场在同一台机器上撞见同一类错误的另一个变种：
>
> ```text
> gh api .../git/trees?recursive=1   →  { "truncated": true }
> ```
>
> GitHub 同样**静默截断**文件树。第一次拿到 6280 个 `SKILL.md`，第二次 56301，
> 两次都不是全量，返回码都是 0。
>
> 这说明它不是"某个 find 用错了"，而是一整类陷阱：**任何会省略掉一部分结果的工具，
> 默认都不会告诉你它省略了。** `find -maxdepth`、GitHub tree API、
> 甚至一个自己写的 `[:40]` 字符串截断，都是同一族。

**顺带更正一个标题口径**：标题里的 7991 是**归档**数量，8003 是**扫描发现**数量，
中间差的 12 个是噪声（散落在下载目录和聊天客户端缓存里的 `SKILL.md`，
其子目录恰好含有 skill）。两个数都对，但混用会让人以为文章算错了。

## 第四个数字：最安静的一个

有 4 个残留的 Docker 卷，名字都很像样：`mcp-sqlite`、`mcp-task-data`、`claude-memory`、
`okta-mcp-server-keyring`。

第一反应写进了给用户的回复："顺手清掉能释放点空间。"

备份完、算完校验和之后才发现：

```text
mcp-sqlite/db.sqlite              0 bytes
mcp-task-data/current-tasks.db    262144 bytes   (28 张表里 27 张是 0 行)
claude-memory/index.js            16673 bytes    (2025-04-30,一年多没动)
okta-mcp-server-keyring/          (空)
```

合计约 **300 KB**。

**代理指标是"存在 4 个卷"，真正该测的是"这 4 个卷里有多少数据"。** 前者是 4，后者接近 0。
而这两个数字之间的差距，只有在真的去打开每个卷的时候才会出现。

这个形状和"PID 文件记的是包装进程"完全一致，方向还相反：
PID 那条会**删错东西**，这条会**让人以为省了 129 GB**。

## 中场：四个形状并排

| 我报的 | 我用的代理指标 | 真正该测的 | 差多少 |
| --- | --- | --- | --- |
| 910 个 MCP server | 扫到了 910 条定义 | 其中多少是**自己拥有的**能力 | 36× |
| Docker 没问题 | 我读了 compose 文件 | Docker 里**到底有什么** | 129.2 GB |
| 1778 个 skill | `find` 报了 1778 | **命令有没有静默截断** | 4.5× |
| 删卷能释放空间 | 存在 4 个卷 | 这 4 个卷里**有多少数据** | 接近 0 |

共同形状：

> **用一个能拿到的表示，去代替一个同样能拿到的权威值；而「它俩差多少」这件事，一次都没量过。**

注意"能拿到"这三个字。四个例子里权威值**一直都可以取到**：
`get_me` 就在工具清单里没调，端口一条查询的事，镜像引用就写在启动参数里。
把这件事说成"环境不支持只好退而求其次"，是给自己一个台阶——而台阶会让人不去查。

## 后记：这篇文章自己被抓了两次

上面四节写完就发布了。发布之后有人**没读文章、直接把引用的那份归档拉下来逐个数字重算**，
找出两处硬伤：

**一，第一张来源表整个数据集用错了**（见第一节补记）。**二，许可证表少了一整类**，
五行相加对不上总数，而每一行的百分比单独看都自洽。

两处都是硬伤，两处我都当场核对确认了是自己错。

值得单独记下来的是**它们为什么没被我自己发现**：

- 第一处：那张表的数字格式规整、量级合理、和上下文"看起来吻合"。**没有任何局部特征会报警。**
- 第二处：每一行都自洽，只有**求和**才会暴露。而我在写的时候根本没有求和——我写的是
  四个我记得的类别，不是从一份完整分类表里抄的。

所以这不属于"我会犯的错"，而属于**"这类错我的自查方式抓不到"**。
自查是对着目标值逐项核，而这两种错的症状是"每项都像对的"。

有效的做法只有一条：**让总数参与判定。** 表必须能加回去，命令必须能在另一套口径下重跑，
数字必须能被一个没读过上下文的人独立复核。

## 中场之二：我把自己当成了泄露发现者

同一个形状，在我自己身上复发了一次，而且这次有代价。

排查脱敏扫描器的告警时，其中一条是：一条 issue 正文里的 `Authorization` 头长度 72，
头两个字符是 `Be`。我把它当成了真实泄露，并且**在对话里断言了两次**：

> 「确认是真漏洞」「多抓出 982 处以前漏掉的带前缀凭据」

然后去核对源文件。原文是：

```bash
export TAVILY_API_KEY="tvly-YOUR_API_KEY_HERE"
```

**是占位符。** 而且脱敏日志里那条记录**压根不存在**——它从头到尾没被我的规则匹配过。

两个错误叠在一起：

1. 我从**掩码后的长度和前缀**推出"这是真的"，没有回去读原文；
2. 真正的缺陷确实存在——`\bapi_key\b` 匹配不到 `TAVILY_API_KEY` 里的 `API_KEY`，
   因为下划线是单词字符，所有带前缀的环境变量名都漏网了。

但这两件事没有关系。**缺陷是真的，推断是假的，而我把推断当成了结论发出去。**

要命的地方在于这条已经进了公开 commit，只能 amend 后 `--force-with-lease` 重推，
并把措辞改掉。代价不是技术上的，是"我说我发现了泄露，结果没有"这件事本身。

真正的教训不是"应该更谨慎"，而是：

> **代理指标不仅会出现在采集环节。它会出现在"我据此下结论"的那一步。**
> 一个看起来像密钥的字符串，和一个真的是密钥的字符串，在掩码之后没有区别。

## 中场之三：工具层的同一个错相

脱敏本身也反复栽在同一个地方。

**第一次：66 处"密钥命中"，只有 1 处是真的。**

```text
原始：headers.Authorization = "Bearer ${VAR}"     ← 引用环境变量
```

正则看到 `Bearer` 加一串字符就报。逐条核实后 66 减到 1。

**第二次：纠偏过头，第一版规则报了 3585 处。**

```text
process.env.API_KEY
this.value
expires_in
```

全是代码标识符，不是凭据。全部替换成 `${SECRET}` 之后 skill 直接不能用了——
归档的目的就是"后面还能直接用"，过度脱敏把这个目的消灭了。

收紧判定（要求值同时含字母和数字、且不是点号分隔的标识符链）之后落到 **325 处真实凭据**，
另有 79 处机器身份路径，合计 404 处。

**第三次：校验器自己在喊狼来了。**

泄漏校验脚本报了十几处"残留 token"，逐条看：

```text
PublicKeyToken=b03f5f7f11d50a3a     ← .NET 程序集强名，微软的公钥标记
Token=test-token-12345               ← 示例代码里的测试固件
```

一个**只会喊"有威胁"的检测器，比没有检测器更糟**，因为你会开始忽略它。
最后给校验器加了一份带理由的白名单：每一条都写清楚为什么它不可能是凭据。

## 中场之四：14 处路径穿越里，13 处是噪音

安全工具报了 14 条 high，我逐条看了。

13 条是：

```python
with open(args.output, "w", encoding="utf-8") as f:
```

`args.output` 是**操作者自己在命令行传的参数**。写到用户指定的位置是 CLI 的正常行为，不是漏洞。

真的那一条在这里：

```python
safe_name = panel_info.replace("/", "_").replace(":", "_").replace(" ", "_")[:40]
filename = f"panel_{pi}_{safe_name}.json"
filepath = os.path.join(output_dir, filename)
```

`panel_info` 来自腾讯云 API 返回的面板名——是**远程数据**。过滤器处理了 `/`、`:` 和空格，
**漏了 `\`**。Windows 上反斜杠是路径分隔符，一个名为 `..\..\..\x` 的面板就能写出 `output_dir` 之外。

向量窄（需要能命名面板的权限），但确实存在，而它就藏在那 13 条噪音中间。

## 再往后：查不到的东西也是数据

最后一块是许可证。7991 个归档的 skill 里：

| 状态 | 数量 | 占比 |
| --- | ---: | ---: |
| MIT | 2283 | 28.6% |
| Apache-2.0 | 469 | 5.9% |
| 上游明确标注 `UNKNOWN` | 384 | 4.8% |
| LICENSE 正文无法归类 | 107 | 1.3% |
| 明确专有 | 56 | 0.7% |
| AGPL | 6 | 0.1% |
| CC | 3 | 0.0% |
| **本地零证据** | **4683** | **58.6%** |

有声明合计 3308，加零证据 4683，正好 7991。

> 这一张表的第一版只列了 MIT、Apache-2.0、专有、AGPL 四类，五类相加对不上总数——
> 漏掉的正好是"上游明确写了 UNKNOWN"和"正文无法归类"这两类共 494 条。
> 而且**每一行的百分比按 7991 反算都自洽**，所以肉眼看每一行都没错，只有加起来才暴露。
> 这也是为什么它当时没被发现：错的不是某一格，是**少了一行**。

那个 4683 不是采集失败，是上游本身没有声明。最大的一个来源目录
（786 个连接器）里连 `plugin.json` 都没有，只有裸目录。24 个上游仓库里也有 6 个在 GitHub 上
没有 license 字段。

当时差一点就把这 4683 个算成"没问题的第三方内容"放过去了。
代理指标是"我没查到它的许可证"，真正该问的是"我有没有权力再分发它"。

## 如果重来，我会先做哪一步

按今天撞出来的次数排序：

**一，先划不做什么。** 成本几乎为零，但它决定后面每一步的判断标准。
「不公开无声明内容」这一条如果在开头没写，后面就会在某个"反正大家都这么做"的时刻被绕过。

**二，任何数字在写下来之前，先去看它到底在数什么。** 不是复核，是去看。
910 要看归属、1778 要看命令的默认行为、4 个卷要打开、66 要读原文。

**三，把"我据此下的结论"也当成采集环节来审。** 这是这次最贵的一条——
我漏掉的那次，不是采集错了，是**从掩码长度推出结论**那一步错了，而采集本身没错。

**四，让总数参与判定。** 一张表必须能加回去，一个数字必须能在另一套口径下重跑。
自查是对着目标值逐项核，但本文第一节和倒数第二节这两种错，逐项核是抓不到的——
它们的症状就是"每项都像对的"。

**五，检测器会喊狼来了，要给它一份带理由的白名单。** 一份白名单同时是文档：
它记录了"我们知道这些形状存在，它们不是威胁"，比多一份干净的报告有用。

## 尾声

这四个错误在当天看起来都很严谨。每一个背后都真跑了一个脚本、真读了一个文件、
真拿到了一个可以写进文章的数字。

所以普通的"检查一下"抓不住它们——**因为检查本身用的就是同一个代理指标。**

能让它们现形的只有一件事：

> **在报出结论之前，去看它到底在数什么。**

具体到这次：去看那 910 个定义里有多少是自己的；去看 `docker images`；
去看 `find` 会不会截断；去打开那 4 个卷；去读那条被掩码的原文到底是什么。

每一步都很便宜。贵的是"不这么做"——尤其是，当不这么做还能让你当场
宣布一个"发现"的时候。

## 附：所有数字都能复核

本文的每个数字都可以在 [mcp-configs](https://github.com/QianChang-official/mcp-configs)
仓库里复核，包括脱敏日志、溯源清单和每一处被替换掉的凭据记录（只存长度和前缀指纹，不存原文）。

校验脚本不做模式匹配就下结论——它从源码里 harvest 出真实的凭据字面量，
再断言这些具体的值没有出现在归档副本里。**模式匹配只能证明"形状"没了，
证明不了"这些值"没了。**
